# 自动巡检重启锁恢复 Spec

## 背景

生产后端在部署重启后，旧进程正在执行的自动巡检被中断，但对应计划仍保留旧实例的“排队中/运行中”状态和长时间锁。新进程启动后只恢复已经过期的锁，因此这些计划会在锁有效期内持续占用全部并发槽位，表现为自动巡检已开启、调度心跳正常，但不再产生新的检测任务。本次事故中 4 个计划因此停止派发，人工清理旧锁后恢复。

## 目标

- 后端重启后自动识别并恢复已失效实例遗留的巡检状态，不等待原锁自然过期。
- 让被部署中断的计划尽快重新进入可派发状态，避免自动巡检整体停摆。
- 保留完整、可追踪的中断结果，不能把被中断任务误报为成功。
- 不影响当前实例仍在正常执行的巡检任务。

## 方案选择

- 推荐方案：单实例部署恢复。新实例启动时，将非当前实例持有的排队中或运行中巡检视为部署中断，统一结束其关联执行记录并立即重新排期。符合当前单后端实例的 Docker Compose 部署方式，恢复快且行为明确。
- 备选方案：仅等待锁超时。实现改动最少，但最长会继续停检数小时，不能满足严重故障的恢复要求。
- 暂不采用：多实例租约与实例存活注册。能支持多副本并行部署，但需要新增实例注册、心跳和失效判定机制，超出本次单周期修复范围。

## 功能需求

- F1: 后端启动时，应识别由非当前实例持有且仍处于排队中或运行中的自动巡检计划，并将其判定为部署中断遗留状态。
- F2: 对已判定为部署中断的计划，应释放遗留占用并立即恢复为可再次派发的状态，不等待原锁到期。
- F3: 对已判定为部署中断的计划，应同步结束其尚未完成的巡检作业、执行尝试和检测运行记录，并明确记录为“部署重启中断”，不得保留为排队中、运行中或成功。
- F4: 当前实例持有且仍在正常执行的计划和关联记录不得被启动恢复流程修改。
- F5: 恢复流程应具备幂等性；同一批中断记录被重复检查时，不得重复创建任务、重复覆盖已完成结果或产生相互矛盾的状态。
- F6: 调度健康状态应能反映恢复结果；恢复完成后不应继续把已中断记录统计为运行中、排队超时或疑似卡住。
- F7: 自动恢复失败时，应保留可诊断且已脱敏的错误信息，同时调度进程继续存活并在后续检查中重试，不得静默停止整个巡检循环。

## 非功能需求

- N1: 本次按当前生产的单后端实例部署模型设计；不得把其他仍存活实例的任务错误回收。未来启用多后端副本前，必须补充实例存活租约机制。
- N2: 恢复操作必须保持计划、作业、执行尝试和检测运行记录之间的状态一致性，避免部分恢复。
- N3: 保持 SQLite 本地开发与 PostgreSQL Docker 部署兼容，不引入 Redis、队列或新的调度基础设施。
- N4: 恢复日志和错误信息不得包含 API Key、鉴权头或其他运行时凭据。
- N5: 保持现有巡检频率、随机派发窗口、最大并发数、异常判定和报告逻辑不变。
- N6: 保留工作区中与本需求无关的未提交修改，只提交本次修复涉及的文档、代码和测试。

## 不做的事

- 不实现多后端副本的完整选主、分布式锁或实例注册中心。
- 不缩短所有正常巡检任务的锁时长来规避问题。
- 不删除被中断任务的历史记录或伪装成正常完成。
- 不改变自动巡检页面的筛选、展示或查询性能逻辑。
- 不修改渠道评分、异常标签、飞书告警和报告结论规则。

## 验收标准

- AC1: 构造一个由旧实例持有、锁仍有数小时才到期且状态为排队中或运行中的计划；启动新后端后，该计划无需等待锁过期即可释放占用并重新进入可派发状态。
- AC2: 上述计划关联的未完成巡检作业、执行尝试和检测运行记录均被结束，并可观察到明确的“部署重启中断”状态或错误说明，不存在遗留的排队中或运行中记录。
- AC3: 恢复后调度器在正常轮询周期内产生新的巡检任务，健康接口显示心跳正常、无由该批遗留记录造成的逾期计划或卡住任务。
- AC4: 构造一个由当前实例持有的正常运行计划；执行恢复检查后，该计划及关联记录保持不变。
- AC5: 对同一批遗留数据连续执行两次恢复检查，第二次不再修改已结束记录、不重复派发任务，状态保持一致。
- AC6: 模拟恢复操作失败时，错误被脱敏记录，调度循环仍继续运行，并能在后续检查成功后完成恢复。
- AC7: 后端相关单元测试和接口测试通过；生产部署重启后，通过真实健康接口与新巡检记录验证自动恢复，不再需要人工执行数据库更新。
