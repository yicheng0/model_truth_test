# 自动巡检重启锁恢复 Tasks

## 文件清单

| 操作 | 文件 | 职责 |
|---|---|---|
| 修改 | `backend/app/services.py` | 扩展调度恢复逻辑，回收旧实例计划及关联记录 |
| 修改 | `backend/app/main.py` | 保证启动恢复异常可诊断且不阻止监督调度启动 |
| 修改 | `backend/tests/test_api.py` | 覆盖旧实例恢复、当前实例保护、幂等和失败重试场景 |

## T1: 建立旧实例恢复的失败测试

**文件：** `backend/tests/test_api.py`

**依赖：** 无

**步骤：**
1. 使用测试数据库创建启用的自动巡检计划，设置 `last_status` 为 `queued` 或 `running`、`locked_by` 为旧实例、`locked_until` 为未来时间。
2. 创建关联的 queued/running `PatrolJob`、running `PatrolJobAttempt`，并创建 pending/running `Run` 记录。
3. 调用现有恢复函数，断言旧实例计划被处理，不等待锁过期。
4. 断言计划锁已释放并重新计算下一次执行时间，关联作业和尝试已结束，运行记录为 `interrupted`，中断原因已记录且不含凭据。

**验证：** 先运行新增测试，期望在实现前因旧实例未来锁未被恢复而失败。

## T2: 增加当前实例保护和幂等测试

**文件：** `backend/tests/test_api.py`

**依赖：** T1

**步骤：**
1. 创建由当前 `SCHEDULER_INSTANCE_ID` 持有且仍在执行的计划及关联记录。
2. 调用恢复函数，断言当前实例计划、作业、尝试和运行记录完全不变。
3. 对同一批旧实例遗留数据连续调用两次恢复函数。
4. 记录两次调用前后的状态和记录数量，断言第二次不重复结束、不重复创建巡检作业或覆盖已完成记录。

**验证：** 运行 T1/T2 对应测试，期望实现前当前实例保护或幂等断言至少有一项失败。

## T3: 实现关联记录收敛和旧实例锁回收

**文件：** `backend/app/services.py`

**依赖：** T1、T2

**步骤：**
1. 将旧实例识别条件从“仅锁已过期”扩展为“计划状态为 queued/running 且锁持有者非当前实例”。
2. 增加按计划收集最近 queued/running 巡检作业及其 running 尝试的处理逻辑。
3. 收集计划最近运行 ID、作业运行 ID和尝试运行 ID，结束其中 pending/running 的 `Run` 并写入部署重启中断原因。
4. 在同一事务中将作业和尝试结束为失败、写入脱敏错误，计划设置失败状态、结束时间、下一次执行时间并清空锁。
5. 保留现有锁过期恢复和超时尝试恢复逻辑，确保旧实例恢复与超时恢复不会互相重复处理。
6. 仅处理重新读取后仍属于非当前实例的记录，避免并发 tick 覆盖当前实例新获得的锁。

**验证：** 运行 T1/T2 对应测试，期望全部通过；运行现有调度恢复和超时相关测试，期望无回归。

## T4: 加强启动恢复和调度循环异常处理

**文件：** `backend/app/main.py`、`backend/app/services.py`

**依赖：** T3

**步骤：**
1. 检查应用生命周期中的启动恢复调用，确保恢复失败只记录脱敏异常，不阻止调度监督任务创建。
2. 检查调度 tick 中的恢复调用，确保数据库回滚后继续执行心跳和后续派发流程。
3. 为恢复失败增加可检索的结构化日志上下文，避免记录 API Key、鉴权头或原始凭据。
4. 保持监督循环对意外退出的自动重启行为不变。

**验证：** 增加恢复异常模拟测试，确认函数抛错时应用仍可启动、调度循环仍可继续；运行相关后端测试。
