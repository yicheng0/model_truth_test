# 自动巡检三分钟窗口随机调度 Spec

## 背景

当前自动巡检可能在同一调度 tick 内同时领取多个到期计划，导致任务列表出现多个完全相同的开始时间和秒数。对于短间隔计划，问题也可能发生在任意秒数，而不是固定在某个 `:00`、`:06` 等时间点；如果短时间内连续抽查，既不能覆盖任意时刻的问题，也会制造重复任务噪音。

## 目标

- 让每个到期的自动巡检轮次在三分钟派发窗口内最多抽查一次。
- 每个计划的抽查秒数独立随机，避免所有渠道在同一秒开始。
- 保留异常发生在窗口内任意秒数时的可观测性，不依赖固定秒数。
- 不改变计划原有的五分钟及以上周期语义。

## 功能需求

- F1: 每个自动巡检计划到达原定执行时间后，在随后三分钟派发窗口内最多创建并启动一次巡检任务；三分钟窗口不改变计划本身的配置周期。
- F2: 每个到期轮次在三分钟派发窗口内随机选择实际开始秒数；不同计划不得因为同一调度 tick 被强制使用相同的开始秒数。
- F3: 调度器在同一 tick 发现多个到期计划时，仍可按可用并发槽位领取，但每个计划的下一次时间必须保留独立随机偏移，不能形成固定秒数或固定批次时间。
- F4: 所有计划继续使用原有的五分钟及以上配置间隔和运行窗口规则；三分钟仅作为每次到期后的派发抖动窗口。
- F5: 计划重试、手动立即执行、锁恢复和运行失败后的重新排程不突破三分钟窗口规则；重试不额外制造同一窗口内的重复正式抽查。
- F6: 任务列表继续展示每次真实巡检的创建、开始和结束时间，能够区分不同窗口的抽查记录。

## 非功能需求

- N1: 随机调度必须可注入确定的随机秒数进行测试，生产运行使用安全的伪随机来源即可。
- N2: 调度计算应保持幂等和可恢复；进程重启、锁过期或多实例竞争不能在同一计划同一窗口产生重复任务。
- N3: 不删除历史任务、不改写历史时间、不影响告警证据和 Request ID 记录。
- N4: 保持现有运行窗口、全局自动巡检开关、并发槽位和计划锁语义。

## 不做的事

- 不把任何计划改成三分钟周期。
- 不改变计划的用户配置值或五分钟及以上周期规则。
- 不通过前端时间格式化掩盖后端重复调度。
- 不增加队列、Redis 或新的持久化表；仅复用现有计划时间、锁和任务记录。
- 不保证不同计划永远不会同秒开始，只要求调度不强制同秒并为每个计划独立随机；极低概率自然碰撞可以存在。

## 验收标准

- AC1: 两个或多个计划同时到期时，本轮实际启动时间分别落在随后三分钟窗口内，且测试注入不同随机秒数时不会相同对齐；各自下一轮仍按原配置周期计算。
- AC2: 同一计划的同一到期轮次在三分钟派发窗口内重复调用调度 tick，只能产生一个 queued/running 任务和一个正式巡检记录。
- AC3: 随机秒数覆盖窗口边界的有效范围，不能产生负数、超过窗口或固定秒数；运行窗口限制仍然生效。
- AC4: 所有计划的下一轮原定时间仍遵循五分钟及以上原配置间隔，现有运行窗口测试继续通过。
- AC5: 失败恢复、锁过期和重试路径不会在同一三分钟窗口内额外创建重复正式抽查。
- AC6: 自动巡检任务列表中的新记录时间不再被同一 tick 强制成完全相同的开始秒数；历史记录保持不变。
- AC7: 后端相关测试、前端测试、生产构建和差异格式检查通过，其他未提交改动保持不变。
