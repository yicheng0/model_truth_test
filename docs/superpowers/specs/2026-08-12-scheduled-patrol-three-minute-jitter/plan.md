# 自动巡检三分钟窗口随机调度 Plan

## 架构概览

在现有后端调度服务中为每个到期轮次增加三分钟随机派发窗口，并将“下一轮原定时间”和“本次实际执行启动时间”分开处理：

```text
计划 next_run_at 到期
  -> 调度 tick 原子领取与推进原配置周期
  -> 为本次 job 生成独立 dispatch jitter
  -> 到达 job due_at 后启动执行
  -> 现有 run / report / alert 流程
```

计划锁仍负责跨 tick 和多实例去重；`next_run_at` 负责每个计划的原配置周期；`PatrolJob.due_at` 负责本次任务在窗口内的实际启动秒数。历史任务不回写。

## 核心数据结构

### 三分钟派发窗口

- `SHORT_PATROL_WINDOW_SECONDS = 180`。
- 每个计划达到 `next_run_at` 后，本轮任务在随后 180 秒内随机派发。
- 派发随机偏移取 1 到 180 秒，边界可通过测试注入；计划配置间隔仍保持五分钟及以上。

### 任务启动时间

- `next_run_at`：计划下一轮被调度器领取的原定时间，继续按配置分钟数计算。
- `PatrolJob.due_at`：本次已领取任务的实际启动时间，使用独立随机偏移，不复用计划的 `next_run_at` 或同一 tick 的统一时间。
- `locked_until`：继续保护计划在 queued/running 状态下不被重复领取。

### 调度状态判定

- `dispatch_window`: 当前到期轮次使用的三分钟派发窗口。
- `dispatch_at`: 当前任务实际允许启动的时间。
- `next_schedule_at`: 当前任务领取后计划按原配置周期计算的下一轮时间。

不新增数据库字段；任务启动时间沿用现有 `PatrolJob.due_at`，调度元数据可记录窗口和抖动秒数以便审计。

## 核心接口

### 下一次调度时间计算

保留现有下一次计划时间计算，使所有计划继续使用配置分钟数和运行窗口校正；移除原有只对五分钟计划混入 1–300 秒的周期改写，避免把计划周期与派发抖动混为一体。

### 任务 dispatch 时间计算

新增纯函数根据领取时间和注入的随机秒数生成 `PatrolJob.due_at`。同一调度 tick 中每个计划分别调用随机源，不共享偏移值；所有自动计划均只对当前到期轮次增加三分钟内抖动。

### 精确延迟启动

调度 tick 领取计划后立即为每个任务创建独立延迟协程，协程精确等待到自身 `due_at` 再开始真实巡检，不能依赖下一次 60 秒 tick，否则同一分钟内到期的任务仍会被对齐到相同秒数。等待期间任务保持 queued、计划保持加锁并占用对应并发槽位。手动立即执行显式绕过 dispatch jitter，但仍通过计划锁避免重复。

## 模块设计

### `backend/app/services.py`

**职责：** 计算三分钟派发窗口、生成独立随机偏移、创建带 `due_at` 的巡检任务，并通过独立延迟协程按精确秒数启动执行。

**依赖：** 现有 SQLAlchemy 计划/任务模型、调度锁、随机模块和异步任务跟踪。

**关键决策：** 不增加迁移；使用现有 `next_run_at`、`PatrolJob.due_at` 和锁字段完成窗口去重和启动抖动。

### `backend/tests/test_api.py`

**职责：** 覆盖派发窗口边界、不同计划独立随机、重复 tick 去重、queued 任务延迟启动、原周期兼容、运行窗口和恢复路径。

### `frontend/src/pages/Runs.tsx`（仅确认）

**职责：** 继续使用后端返回的真实创建/开始/结束时间；本次不改前端时间格式或列表排序。

## 模块交互

1. 计划创建或执行完成时计算下一次 `next_run_at`。
2. 调度 tick 只领取 `next_run_at <= now` 且未加锁的计划，并立即推进到下一个随机窗口。
3. 领取时为本次 PatrolJob 写入独立 `due_at`，保存窗口/抖动元数据，并立即建立受跟踪的延迟协程。
4. 每个延迟协程独立等待到 `due_at`，然后启动真实巡检；因此不同随机秒数不会被 60 秒 tick 再次对齐。
5. 执行完成、失败、重试和锁恢复继续复用现有释放锁与下一次排程路径；重试沿用同一正式任务，不新增窗口外重复任务。

## 技术决策

| 决策点 | 选择 | 理由 |
|---|---|---|
| 窗口状态存储 | 复用 `next_run_at` | 已是计划级调度游标，避免迁移和历史数据改写 |
| 实际启动抖动 | 复用 `PatrolJob.due_at` | 任务已有到期时间，能让同一 tick 的任务真正错开开始 |
| 去重保护 | 现有计划锁 + queued/running 任务 | 覆盖多实例、重复 tick、锁恢复，不新增基础设施 |
| 派发窗口 | 每个到期轮次 180 秒 | 与用户要求的 3 分钟随机抽查窗口一致，不改变任何计划周期 |
| 随机测试 | 注入随机秒数 | 生产保持随机，测试可稳定验证边界和不对齐行为 |
| 前端范围 | 不改列表展示 | 截图中的相同时间是后端调度行为，前端继续展示真实时间即可 |
