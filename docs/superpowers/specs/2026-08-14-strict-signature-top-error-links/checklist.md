# 顶部巡检异常严格分类与直达详情 Checklist

> 每项均通过运行代码或观察行为验证。

## 严格异常口径

- [x] HTTP 403 且错误为“渠道已被禁用”的巡检记录不进入顶部错误总数（验证：创建该证据并请求严格异常摘要，期望 `strict_total` 不增加）。
- [x] HTTP 403“渠道已被禁用”的任务不出现在顶部错误列表（验证：打开 `/runs`，检查顶部区域不存在该任务名称）。
- [x] HTTP 403“渠道已被禁用”不显示为“Thinking Signature 无效”（验证：检查顶部和下方异常提示均无该分类）。
- [x] 网络错误不进入严格异常摘要（验证：构造网络失败报告，期望严格总数和条目不增加）。
- [x] 超时不进入严格异常摘要（验证：构造请求超时报告，期望严格总数和条目不增加）。
- [x] HTTP 5xx 不进入严格异常摘要（验证：构造 500 或 503 报告，期望严格总数和条目不增加）。
- [x] 权限或访问受限不进入严格异常摘要（验证：构造 access forbidden、permission denied 或渠道禁用报告，期望严格总数和条目不增加）。
- [x] 额度、配额或余额不足不进入严格异常摘要（验证：构造额度故障报告，期望严格总数和条目不增加）。
- [x] 无可用渠道或账号不进入严格异常摘要（验证：构造对应运营故障报告，期望严格总数和条目不增加）。
- [x] `signature_ok=null` 不进入 Signature 异常摘要（验证：构造未完成验证证据，期望 Signature 分类计数不增加）。
- [x] 仅有 `signature_interop_failed` 历史标签但无明确错误文本时不进入 Signature 异常摘要（验证：构造历史报告，期望不显示该任务）。
- [x] 普通失败状态、低评分或通用异常标签不能单独生成顶部严格异常（验证：构造失败任务但不包含两类明确证据，期望顶部为空）。
- [x] HTTP 400 且明确包含 `Invalid signature in thinking block` 时进入 Signature 异常摘要（验证：请求接口后看到 Signature 分类计数增加）。
- [x] 明确 Signature 错误的大小写和引号变体仍能正确识别（验证：使用多种等价错误文本，期望均被识别）。
- [x] Kiro 身份泄漏继续进入严格异常摘要（验证：构造明确 Kiro 身份自报，期望 Kiro 分类和严格总数增加）。

## 服务端严格摘要

- [x] 严格异常摘要响应包含去重后的 `strict_total`（验证：请求 `/api/runs/patrol/anomalies`，检查字段和数值）。
- [x] 严格异常摘要响应包含最多 10 条 `strict_items`（验证：构造超过 10 条明确异常，期望条目数为 10）。
- [x] 超过 10 条异常时 `strict_total` 保持完整真实数量（验证：构造 17 条异常，期望总数为 17、条目为 10）。
- [x] 严格条目只存在 Kiro 和 Signature 两种类型（验证：检查所有 `kind`，不得出现通用巡检异常）。
- [x] Kiro 条目排在 Signature 条目前（验证：混合两类异常并检查返回顺序）。
- [x] 同一类型按发生时间从新到旧排序（验证：使用乱序时间数据，检查响应顺序）。
- [x] 同一任务同时命中 Kiro 和 Signature 时 `strict_total` 只计一次（验证：检查去重总数）。
- [x] 同一任务同时命中两类时 `strict_items` 只显示一条 Kiro（验证：检查任务标识和类型）。
- [x] 两个分类组仍分别保留其真实分类计数和任务入口（验证：同一任务双命中时检查两个组及严格去重总数）。
- [x] 渠道筛选会同步收窄严格总数、严格条目和两个分类组（验证：分别请求全部渠道与指定渠道并核对数据）。
- [x] 严格摘要不包含完整错误正文、原始请求、原始响应或认证信息（验证：检查接口响应字段和序列化内容）。

## 顶部错误日志

- [x] 顶部错误日志只读取严格异常摘要，不再请求顶部专用 `errors_only=true` 通用分页（验证：记录首屏网络请求，检查不存在额外顶部通用错误请求）。
- [x] 顶部标题数量使用 `strict_total`，不使用通用错误数量（验证：严格异常为 2、通用错误为 5 时，标题显示 2）。
- [x] 顶部只展示“Kiro 身份泄漏”和“Thinking Signature 无效”标签（验证：检查顶部 DOM，不存在“巡检异常”）。
- [x] 每条顶部异常显示错误类型、渠道、任务名称和时间（验证：检查每一行四类信息）。
- [x] 顶部任务名称链接到对应 `/runs/{run_id}`（验证：检查链接地址）。
- [x] 点击顶部任务名称后直接进入对应详情页（验证：点击后检查 URL 和任务详情内容）。
- [x] 列表首屏不提前请求任务完整结果（验证：点击前 `/api/runs/{id}/results` 请求数为 0）。
- [x] 只有运营故障或无严格异常时显示“暂无需要处理的错误”（验证：使用空严格摘要并检查空状态）。
- [x] 顶部不展示完整错误正文、Request ID、原始请求或原始响应（验证：检查 DOM 不包含 fixture 中的证据正文）。
- [x] 严格摘要加载失败时只显示顶部局部错误和重试入口（验证：让摘要接口返回 500，普通任务表仍有数据）。
- [x] 严格摘要延迟时普通任务表先展示并可操作（验证：延迟摘要响应，检查普通任务表可见）。
- [x] 严格异常超过 10 条时显示真实总数和“查看全部异常”（验证：使用 17 条 fixture，检查标题、10 行和按钮）。
- [x] 点击“查看全部异常”只滚动到下方严格异常提示区域，不开启通用“只看错误”（验证：检查视口位置和 `aria-pressed` 保持原值）。

## 端到端场景

- [x] HTTP 403“渠道已被禁用”巡检失败 -> 打开 `/runs` -> 顶部总数不增加且无 Signature 提示 -> 在下方历史或详情仍可查看该请求证据。
- [x] HTTP 400 `Invalid signature in thinking block` -> 打开 `/runs` -> 顶部显示“Thinking Signature 无效” -> 点击任务名称直接进入该任务详情并看到 Signature 请求日志。
- [x] 同一任务同时出现 Kiro 与明确 Signature -> 顶部总数只增加 1 -> 顶部只显示“Kiro 身份泄漏” -> 下方两个分类组仍保留各自证据入口。
- [x] 严格异常 17 条且通用错误数量更多 -> 顶部标题显示 17、仅 10 行、无通用异常 -> 点击“查看全部异常”滚动到下方严格提示且不切换通用错误筛选。
- [x] 当前渠道只有运营故障 -> 顶部显示“暂无需要处理的错误” -> 普通任务表和下方巡检筛选、分页、详情继续可用。
- [x] 严格摘要接口返回 500 -> 顶部显示局部加载失败 -> 普通任务表和下方巡检日志仍可操作。
