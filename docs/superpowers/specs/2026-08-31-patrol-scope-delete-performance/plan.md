# 自动巡检日志范围删除性能修复 Plan

## 架构概览

新增巡检专用的“按筛选范围删除”接口。前端确认后只提交当前 `channel_id` 与 `errors_only`，后端复用巡检列表的筛选语义，在同一事务内选出已结束日志并执行现有集合删除。现有 ID 批量删除接口继续供“删除已选”使用。

## 核心接口

### `POST /api/runs/patrol/delete-scope`

请求：

- `channel_id`: 可选；为空表示全部渠道。
- `errors_only`: 布尔值；与页面“只看错误”一致。

响应：

- `matched`: 本次范围内进入删除预检的已结束日志数。
- `deleted`: 实际删除数。
- `failed`: 因基线引用等业务约束未删除的日志及原因。

接口继续使用现有管理员权限校验。`pending`、`running` 不进入删除集合。

## 模块设计

- 后端筛选：抽取巡检范围条件构造逻辑，由列表计数、分页和范围删除共同复用，防止渠道/错误口径漂移。
- 后端删除：一次查询取得范围内终态 run ID，复用现有预检、500 条分批集合清理、关联记录删除和计划最新运行引用回退逻辑，最后单次提交事务。
- 前端 API：增加范围删除方法；“删除当前范围”不再循环调用分页列表，也不再发送 6002 个 ID。
- 前端页面：范围按钮调用新接口；“删除已选”仍调用 `/api/runs/bulk-delete`。成功后统一刷新巡检列表、异常摘要和报告，并显示实际删除/失败数量。
- 数据库：不新增表、索引或迁移；继续兼容 SQLite 与 PostgreSQL。

## 关键技术决策

- 选择同步范围删除：临时 SQLite 中现有集合清理 6002 条完整关联数据约 0.204 秒，主要瓶颈是前端约 61 次串行列表查询。
- 不复用通用 ID 请求体：避免浏览器分页取 ID、超大请求体和筛选快照漂移。
- 保留现有集合删除实现：它已支持分批参数、关联表清理和计划引用修复，风险最小。
- 删除条件以服务端执行时为准；确认框数量是确认时快照，如并发巡检刚结束，最终成功数以响应为准。
- 业务引用冲突不回滚其他可删除日志，继续通过 `failed` 返回。

## 验证设计

- 后端：覆盖全部渠道、指定渠道、只看错误、组合筛选、未结束日志、基线冲突、关联清理和计划引用回退。
- 性能：构造 6002 条带结果、报告、告警、巡检任务/尝试的日志，范围删除小于 5 秒。
- 前端：断言范围删除只编码筛选参数；删除已选契约不变。
- 浏览器：点击范围删除后无分页收集请求，仅有一次新删除请求；刷新后的数量、pending/running 保留正确。
- 完整验证：后端全套 pytest、前端测试、生产构建、浏览器回归和 `git diff --check`。
