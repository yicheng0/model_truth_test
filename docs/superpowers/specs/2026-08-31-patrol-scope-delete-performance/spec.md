# 自动巡检日志范围删除性能修复 Spec

## 背景

“删除当前范围”会由浏览器逐页加载当前筛选范围内的全部日志，收集 ID 后再提交删除。约 6000 条日志需要数十次串行查询，导致线上几分钟无法完成。

## 目标

- 将当前范围删除改为一次服务端范围删除操作。
- 6000 条量级的已结束巡检日志在正常线上负载下于 15 秒内完成。
- 保持渠道筛选、只看错误、未结束日志保护和关联数据清理语义不变。

## 功能需求

- F1: 用户确认后，系统直接删除当前渠道与错误筛选共同限定范围内的全部已结束巡检日志。
- F2: 删除范围必须与按钮显示数量和确认文案一致；未结束日志必须跳过。
- F3: 同时删除日志对应的结果、报告、关联告警和巡检任务记录，并修复相关计划的最新运行引用。
- F4: 删除完成后刷新日志、异常摘要和报告数据，并明确展示成功数量及未删除原因。
- F5: “删除已选”和单条删除保持现有行为，不受本次改动影响。

## 非功能需求

- N1: 删除请求数量不随日志页数增长，确认后不得再逐页读取列表。
- N2: 6002 条完整关联测试数据的自动化性能场景应在 5 秒内完成；线上正常负载目标为 15 秒内。
- N3: 保持 SQLite 与 PostgreSQL 兼容，不引入队列、Redis 或后台任务系统。
- N4: 保持管理权限校验、凭据安全和现有事务一致性。
- N5: 仅修复范围删除链路，不扩展其他批量管理功能。

## 不做的事

- 不新增删除进度任务页或异步任务状态。
- 不改变巡检日志筛选、排序和分页规则。
- 不删除 pending 或 running 日志。
- 不改造普通检测任务、告警或报告的独立删除入口。

## 验收标准

- AC1: 6002 条范围删除确认后只产生一次删除请求，且不会产生用于收集 ID 的分页列表请求。
- AC2: 全部渠道、指定渠道、只看错误及渠道加错误四种范围均只删除对应已结束日志。
- AC3: pending/running 日志保留，按钮计数与实际可删除数量一致。
- AC4: 结果、报告、告警、巡检任务记录均被清理，计划最新运行引用正确回退。
- AC5: 6002 条完整关联数据自动化场景在 5 秒内完成，线上正常负载验证在 15 秒内完成。
- AC6: 后端测试、前端测试、生产构建和浏览器删除回归全部通过。
