# o5 缓存测试 temperature 兼容修复 Plan

## 架构概览

保持现有缓存测试调用链不变，只收窄缓存探针自身的请求参数：缓存测试服务继续构造包含长文本和 `cache_control` 的手工测试用例，经现有渠道调用器发送；请求参数中不再加入 `temperature`。其他测试套件和参数行为探针不复用本次改动。

```text
缓存测试 API
  -> 缓存测试服务构造探针
  -> 仅携带 max_tokens、system cache_control 和用户消息
  -> 现有渠道调用器
  -> 持久化原始请求、响应、usage 与缓存统计
```

## 核心数据结构

### 缓存探针请求参数

- `max_tokens`: 保持现有值，用于限制响应长度。
- `system_content`: 保持现有长文本、独立探针标记和缓存有效期。
- `temperature`: 不再由缓存探针设置，因此不会进入预热或重复请求。

### 缓存测试结果

保持现有结果结构不变，包括预热结果、重复请求结果、缓存写入/读取 token、请求命中率、Token 命中率、请求 ID、协议和端点。

## 核心接口

### `create_cache_hit_rate_test`

**职责：** 创建并执行缓存预热与重复请求，汇总缓存使用证据。

**接口变化：** 对外 API 和返回结构均不变；仅调整其内部构造的缓存探针参数，使所有尝试均不携带 `temperature`。

## 模块设计

### 缓存测试服务

**职责：** 从缓存探针专用参数中移除固定采样温度，同时保留 `max_tokens` 和缓存系统内容。

**依赖：** 继续使用现有手工测试用例构造、渠道调用和结果持久化逻辑。

### 后端回归测试

**职责：** 在现有缓存测试主流程用例中检查预热与全部重复请求的持久化原始请求均不含 `temperature`；继续检查缓存标记、长文本、TTL、统计和凭据脱敏。

## 模块交互

1. API 接收缓存测试次数、间隔和 TTL。
2. 服务生成独立探针标记和带 `cache_control` 的长文本系统内容。
3. 服务构造不含 `temperature` 的探针参数。
4. 现有调用器对预热和重复请求使用同一测试用例，因此所有请求均不含该参数。
5. 现有持久化与汇总逻辑记录缓存 usage 和命中率。

## 技术决策

| 决策点 | 选择 | 理由 |
|---|---|---|
| 参数处理位置 | 在缓存探针构造源头移除 `temperature` | 所有预热和重复请求一次生效，避免下游分支遗漏 |
| 模型判断 | 不判断 o5 或其他模型名 | 缓存测试本身不依赖温度，且模型名可能有别名或被代理改写 |
| 错误重试 | 不增加弃用错误后的重试 | 避免额外失败请求污染次数、成本和延迟证据 |
| 测试方式 | 扩展现有缓存主流程集成测试 | 能直接验证最终持久化的真实请求形态，而非只测试局部字典 |
| 兼容范围 | 不改通用调用器和专用参数探针 | 防止削弱 Thinking temperature 等协议检测能力 |
