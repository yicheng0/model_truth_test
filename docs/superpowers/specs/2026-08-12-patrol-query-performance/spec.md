# 自动巡检日志查询性能优化 Spec

## 背景

自动巡检日志页面当前先加载全部历史日志，然后为每条日志分别加载完整运行结果。完整结果包含渠道、逐项结果、对比、报告和基线数据，导致页面在历史日志较多时产生大量并发请求，首屏长时间显示“加载中”，并增加后端数据库和网络负载。

## 目标

- 让自动巡检日志首屏只加载列表展示和筛选所需的轻量摘要。
- 让“只看错误”能够基于服务端摘要准确筛选并统计全部历史日志。
- 只有用户展开行或进入详情时，才加载该条日志的完整证据。
- 保留现有排序、渠道筛选、分页、删除、展开和详情行为。

## 功能需求

- F1: 自动巡检日志列表返回每条日志所需的轻量摘要，包括运行状态、错误/复审状态、是否存在证据以及巡检渠道信息。
- F2: 列表支持服务端分页，能够按页码和每页条数返回日志，并返回筛选后的总数量。
- F3: 列表支持服务端错误筛选；开启“只看错误”时只返回异常或需要复审的日志，正常日志不进入列表和错误计数。
- F4: 渠道筛选、错误筛选、分页和每页条数可以组合使用，切换筛选条件后回到第一页，列表顺序保持按创建时间倒序。
- F5: 列表初始化和翻页不请求每条日志的完整结果接口；展开行或进入详情时才请求对应日志的完整证据。
- F6: 完整证据接口继续返回现有详情所需的结果、对比、报告和基线数据，展开行和详情页的数据内容不减少。
- F7: 当前页日志加载失败时显示可识别的列表错误状态，并允许重试；单条详情加载失败不阻塞其他列表行。

## 非功能需求

- N1: 首屏自动巡检日志列表的请求数量与当前页大小同量级，不随历史日志总量线性增长。
- N2: 列表响应不包含完整逐项结果、对比和基线结果，减少响应体积和序列化开销。
- N3: 服务端查询使用现有数据模型和索引，保持 SQLite 本地模式与 PostgreSQL Docker 模式兼容。
- N4: 不持久化 API Key、鉴权头或其他运行时凭据；摘要和详情继续使用脱敏字段。
- N5: 不修改普通检测任务列表、评分规则、异常分类边界、告警逻辑或数据库中已有证据内容。
- N6: 保留工作区中与本需求无关的未提交修改，只暂存和提交本次性能优化涉及的文件。

## 不做的事

- 不引入 Redis、消息队列、缓存服务或新的数据库迁移。
- 不删除或裁剪完整证据接口中的现有字段。
- 不在列表默认展示完整错误正文；错误详情仍通过展开行或详情页查看。
- 不改变历史日志的排序规则或已有删除权限。
- 不以增加前端并发度、延迟加载全部历史日志详情或扩大浏览器缓存作为主要方案。

## 验收标准

- AC1: 打开自动巡检日志页面时，列表请求不再按历史日志条数发起完整结果请求；在 200 条历史日志、每页 10 条的场景下，首屏完整结果请求数为 0，列表请求数量不超过页面所需的固定请求数。
- AC2: 列表默认展示第一页日志并显示服务端总数量；切换到下一页后只显示对应页的日志，页码和总页数正确。
- AC3: 开启“只看错误”后，服务端返回的列表只包含异常或需要复审日志，正常日志不显示且不计入错误数量；关闭后恢复全部日志。
- AC4: 同时选择渠道和“只看错误”时，只返回同时满足条件的日志；切换任一筛选或每页条数后回到第一页，创建时间倒序不变。
- AC5: 默认列表加载完成后，展开一条日志或进入详情才产生该日志的完整结果请求；展开内容和详情页仍包含现有完整证据字段。
- AC6: 列表摘要查询失败时页面显示错误状态并可重试；一条日志的详情查询失败时不影响其他行和分页操作。
- AC7: 后端接口测试、前端组件/单元测试、生产构建通过，并用浏览器在真实 `/runs` 页面验证首屏请求数、错误筛选、翻页和展开详情行为。
