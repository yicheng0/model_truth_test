# 自动巡检日志直接展示错误 Spec

## 背景

自动巡检日志表格目前主要显示“正确”“异常”“需要复审”和各探针状态。具体错误虽然已经保存在巡检证据中，但通常需要悬浮、展开行或进入详情才能看到，排查多个渠道时效率较低。

## 方案选择

- 方案 A（采用）：在每条异常巡检日志的“巡检结果”区域直接显示一行精简错误内容，完整错误仍可悬浮或展开查看。无需新增列，移动端和窄屏更容易保持布局稳定。
- 方案 B：新增独立“错误”列。扫描更直观，但会进一步加宽已有横向表格，并在正常日志中产生大量空白。
- 方案 C：只在点击后弹窗显示。信息完整，但仍需要额外操作，不满足“直接展示”的要求。

## 目标

- 在自动巡检日志列表中无需悬浮、展开或进入详情即可看到错误原因。
- 保持错误类型语义准确，运营故障不得被展示成 Signature 异常。
- 保持表格紧凑、可扫描，不让超长上游响应破坏布局。

## 功能需求

- F1: 每条存在错误的已结束巡检日志，在“巡检结果”区域直接展示一段可读错误正文。
- F2: 直接展示内容优先使用具体上游错误；其次使用 Signature 明确拒绝原因、探针错误或已有异常说明，不只显示内部标签。
- F3: 网络错误、超时、5xx、额度不足、资源池不可用等运营错误直接显示其运营错误内容，但不得标记为 Signature 失败。
- F4: 明确的 `Invalid signature in thinking block` 错误显示为 Signature 错误；普通包含 `signature` 单词的网络或超时错误仍按运营错误显示。
- F5: 正常日志不显示错误正文；请求日志加载失败时直接显示“日志加载失败”及可读失败原因。
- F6: 错误正文在表格中限制为紧凑长度，超出部分截断；用户仍可通过悬浮、展开或详情查看完整脱敏错误。
- F7: 错误展示随渠道筛选、分页和轮询刷新同步更新，不改变现有排序、删除、复审和详情操作。

## 非功能需求

- N1: 复用现有巡检证据和错误字段，不新增后端接口或数据库字段。
- N2: 直接展示的内容必须使用现有脱敏数据，不展示 API Key、鉴权头、完整签名或其他凭据。
- N3: 错误分类和错误文案提取使用同一套规则，避免列表、展开详情和报告给出互相矛盾的结论。
- N4: 错误文本不得撑高到影响日志快速扫描；长单词、JSON 和 request ID 不得溢出单元格。
- N5: 保留用户当前未提交的 Claude Code 前端改动，不覆盖或混入本次功能。

## 不做的事

- 不新增独立错误管理页面或错误搜索功能。
- 不修改 Signature、运营故障或真伪判断的后端规则。
- 不直接展示完整原始请求、鉴权信息或未脱敏响应。
- 不修改普通检测任务列表和其他页面的错误展示。
- 不因某条日志存在运营错误而自动创建 Signature 异常告警。

## 验收标准

- AC1: 构造一条普通探针错误，在自动巡检日志列表中不进行任何悬浮或点击即可看到具体错误正文。
- AC2: 构造网络超时、503、额度不足和资源池不可用错误，列表直接显示对应运营错误，且不出现“Signature 失败”误导。
- AC3: 构造明确 `Invalid signature in thinking block` 错误，列表显示 Signature 错误；构造 `signature validation timed out` 时列表显示超时运营错误而非 Signature 失败。
- AC4: 正常日志只显示正常状态，不出现错误行；巡检详情接口加载失败时列表直接显示加载失败原因。
- AC5: 超长错误和 JSON 在列表内被截断且不溢出布局，悬浮或展开后能看到完整脱敏内容。
- AC6: 切换渠道、页码和每页条数后，每行错误仍与对应日志一致；删除、复审、展开和查看详情行为不回归。
- AC7: 错误提取与分类测试、前端全量测试、生产构建和真实浏览器列表验收通过。
